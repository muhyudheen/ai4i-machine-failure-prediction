# AI in Manufacturing: Machine-Failure Prediction & Operating-Range Optimisation

Predict machine failure from process parameters, explain which parameters drive it, and recommend
low-risk operating ranges, using the **AI4I 2020 Predictive Maintenance Dataset** (UCI id 601).

## 1. Problem framing

| | |
|---|---|
| Data | 10,000 machining runs, 0 missing values, 0 duplicate rows |
| Inputs | Product quality `Type` (L/M/H), air temperature [K], process temperature [K], rotational speed [rpm], torque [Nm], tool wear [min] |
| Target | `Machine failure` (binary) |
| Imbalance | **339 failures = 3.39 %**, i.e. **28.5 : 1** |
| Task | Imbalanced binary classification, then explanation, then an optimisation layer that recommends operating ranges |

Because 96.6 % of runs do not fail, a model that always says "no failure" scores **96.6 % accuracy** and is useless.
Every modelling choice below follows from that.

## 2. The three decisions that matter (and where they live in the code)

### 2.1 Leakage: the five failure-mode flags are dropped
`TWF, HDF, PWF, OSF, RNF` (tool wear, heat dissipation, power, overstrain, random failure) are *outcomes*, not
process inputs. `Machine failure` is almost exactly their logical OR: the OR alone gives 97.3 % recall at 94.8 %
precision, with no model at all. Keeping them in the feature matrix yields a fake ~100 % score. They are removed in
`src/data.get_X_y`, the only place the feature matrix is built, and an `assert` guards it. `UID` and `Product ID` are
also dropped: they are unique per row, and the ID's letter prefix just duplicates `Type`.

> Data note: the OR relation is *not* exact. 18 runs have `RNF = 1` but `Machine failure = 0`, and 9 failures have no
> mode flag. The target is kept as given (notebook 01, §3).

### 2.2 SMOTE only inside each training fold
Resampling is a step inside an **`imblearn.pipeline.Pipeline`** (`src/pipeline.py`). imblearn samplers run only during
`fit` and are skipped during `predict`/`predict_proba`. In cross-validation, `fit` only ever sees the training fold, so
synthetic failures are built from training rows and **the validation fold is never resampled**. We never resample
before splitting. Notebook 02 §5 does it the wrong way on purpose to show the effect: SMOTE-before-split reports a
fake **PR-AUC 0.999** versus **0.872** done correctly. We use SMOTENC so the categorical `Type` stays a valid category
rather than being interpolated.

### 2.3 PR-AUC is the primary metric; accuracy is reported but never used for selection
With 3.4 % positives, ROC-AUC looks flattering: logistic regression scores 0.92 ROC-AUC but only 0.50 PR-AUC.
PR-AUC (average precision) uses only precision and recall on the failure class, its chance level is the prevalence
(0.034), and it is threshold-free. That matters because class weighting and SMOTE shift predicted probabilities, so
metrics at a fixed 0.5 cut-off do not compare fairly across strategies (`src/cv.py`).

## 3. Method

- **Validation:** stratified 5-fold CV with a fixed seed (42). Every configuration is scored on **identical folds**, so
  differences between configurations are paired comparisons. Every metric is reported as mean ± std over the folds.
- **Preprocessing:** `Type` is ordinal-encoded L < M < H (failure rate is monotone: 3.9 % > 2.8 % > 2.1 %), and numeric
  features are standardised inside a `ColumnTransformer`. Trees do not need scaling, but SMOTE's nearest-neighbour
  search does; scaling changes no tree splits, so all models share one preprocessing path.
- **Physics features** (`src/features.py`), each mirroring a failure mechanism:
  `power = torque × angular speed [W]` (PWF), `temp_diff = process − air temperature` (HDF),
  `overstrain = tool wear × torque` (OSF).
- **Grid:** {Logistic Regression, Random Forest, XGBoost} × {no resampling, class weighting / `scale_pos_weight`,
  SMOTE in-fold} × {with, without physics features} = 18 configurations.
- **Hyper-parameter tuning:** **nested** CV (inner 3-fold randomised search scored by average precision, outer = the
  same 5 folds) for RF and XGBoost, with the same budget for both.
- **Threshold:** chosen for **recall ≥ 90 %** (a missed failure costs more than an inspection), and evaluated with
  **nested** CV: the threshold is picked inside each outer training fold and scored on the untouched outer test fold.

## 4. Results

Full tables: [`reports/metrics.md`](reports/metrics.md) (generated by notebook 02).

### 4.1 Model × imbalance strategy (physics features; PR-AUC mean ± std, 5 folds)

| | No resampling | Class weighting | SMOTE (in-fold) |
|---|---|---|---|
| Logistic Regression | 0.495 ± 0.048 | 0.452 ± 0.050 | 0.431 ± 0.060 |
| Random Forest | **0.905 ± 0.008** | 0.892 ± 0.014 | 0.878 ± 0.009 |
| XGBoost | 0.872 ± 0.019 | 0.875 ± 0.017 | 0.872 ± 0.013 |
| *RF, tuned (nested CV)* | **0.915 ± 0.006** | | |

### 4.2 Key findings
- **Physics features help a lot:** +0.08 to +0.14 PR-AUC for every tree configuration, and better on 5/5 paired folds
  each time. Trees split on one feature at a time, so a boundary on a product (power, wear × torque) costs them many splits.
- **Imbalance handling did not raise PR-AUC** for any model. Class weighting and SMOTE shift probabilities, which buys
  recall at the 0.5 cut-off with precision. That is the same trade the threshold makes, only less transparently.
- **Random Forest beats XGBoost** by +0.040 ± 0.014 PR-AUC (wins 5/5 paired folds). Tuning RF added +0.010, and the
  inner search chose the same hyper-parameters in every outer fold. Tuning XGBoost did not help.

### 4.3 Selected model and operating threshold
**Random Forest**, physics features, no resampling, `max_depth=8, max_features=0.8, min_samples_leaf=2`, 400 trees.

| Operating point | PR-AUC | ROC-AUC | Recall | Precision | F1 | Accuracy *(misleading)* |
|---|---|---|---|---|---|---|
| threshold 0.5 | 0.915 ± 0.006 | 0.978 ± 0.007 | 0.817 ± 0.026 | 0.982 ± 0.017 | 0.892 ± 0.017 | 0.993 ± 0.001 |
| **threshold 0.056 (recall ≥ 90 %, nested)** | 0.915 ± 0.006 | 0.978 ± 0.007 | **0.894 ± 0.016** | **0.522 ± 0.036** | 0.658 ± 0.026 | 0.968 ± 0.004 |

Across the 5 test folds, the tuned threshold catches **26 more failures** (277 → 303 of 339) at the cost of **275 more
false alarms** (5 → 280, i.e. 2.9 % of healthy runs flagged). Accuracy *falls* while the model gets better at its job.

## 5. Interpretability (notebook 03)

- **Drivers:** temperature difference (low means risk), overstrain = wear × torque (high means risk), speed (low means
  risk) and power, which is **two-sided**: both too low and too high are risky. That U-shape is something a linear
  model cannot express. As *raw inputs*, torque and speed carry the most out-of-fold signal (PR-AUC drops by 0.80 and
  0.64 when shuffled), because they feed both power and overstrain.
- **SHAP** (TreeSHAP, probability units, additivity checked): global beeswarm plus three waterfalls (a caught
  overstrain failure, a caught heat-dissipation failure, and a missed failure).
- **The missed failure** is one of the 9 runs with no failure-mode flag. Its settings are unremarkable, and models that
  never saw it give it P = 0.000. Failures like this are not explained by the process parameters, so recall cannot
  reach 100% on these inputs.

## 6. Optimisation: recommended operating ranges

Exhaustive grid search over the controllable parameters: speed × torque (141 × 151 grid) and tool wear. Ambient
temperatures are held at their medians. Two safeguards:
1. **Data support:** only settings with training runs nearby are considered. Speed and torque are strongly coupled
   (ρ = −0.92), so about 90% of the rectangle is never observed, and a tree model only extrapolates there.
2. **Risk budget, not alarm threshold:** a setting is *safe* if P(failure) ≤ **1%** at every tool wear up to the
   limit. The 0.056 alarm threshold answers a different question ("flag this run?"). It sits on the ~5% plateau
   caused by random tool-wear failures, and would accept 220–232 min of wear. Budgets from 0.5% to 2% give the same answer.

| Type | Change tool before | Power band | Max torque | Min speed if ΔT ≈ 8 K | Robust set-point |
|---|---|---|---|---|---|
| L | 202 min | 4.75–7.75 kW | 54.0 Nm | 1,390 rpm | 1,488 rpm · 43.5 Nm |
| M | 202 min | 4.75–8.00 kW | 58.5 Nm | 1,390 rpm | 1,500 rpm · 42.5 Nm |
| H | 202 min | 4.75–7.75 kW | 54.0 Nm | 1,390 rpm | 1,500 rpm · 42.5 Nm |

**Checked against the physics.** The dataset's failure modes follow documented rules, and we first confirmed each one in
the data (100% agreement for PWF, HDF and OSF). The model never saw the mode flags, yet it recovered:

| Mechanism | Model-implied | Dataset rule |
|---|---|---|
| Power failure | safe band 4.75–8.0 kW | fails outside 3.5–9 kW (model is conservative, as it should be) |
| Heat dissipation | needs ≥ 1,390 rpm when ΔT ≈ 8 K | fails if ΔT < 8.6 K and speed < 1,380 rpm |
| Tool wear | change before 202 min | random failures at 198–253 min |
| Overstrain, L / M | wear × torque ≤ 10.9k / 11.8k | fails above 11k / 12k min·Nm |
| Overstrain, H | ≤ 10.9k | fails above 13k (**conservative**: only 12 H runs have high wear and high torque) |

## 7. Dashboard (`app.py`)

1. **Model performance:** the CV table (model × strategy, mean ± std, toggle for physics features); interactive PR
   and ROC curves; and a **threshold slider** that updates recall, precision, false alarms and the confusion matrix live,
   using out-of-fold predictions.
2. **Explainability:** SHAP summary, impurity and permutation importance, partial dependence.
3. **What-if simulator:** sliders for Type and the 5 process parameters. It shows live P(failure) with status (within
   budget / elevated / alarm), the most likely failure mode with all five mode probabilities, the physics quantities
   next to their rule limits, a per-prediction SHAP waterfall, and a warning when the setting is outside the training data.
4. **Operating ranges:** the recommendation table, plus an interactive risk map (Type, tool wear, air temperature,
   temperature difference) drawn only over data-supported settings.

## 8. Limitations

- AI4I 2020 is **synthetic**: its failure modes are simple rules. That is what makes the physics check possible, but
  real machines will be noisier, and these exact numbers should not be transferred to real equipment.
- Operating ranges hold non-varied parameters at their medians. The dashboard's risk map explores other conditions.
- Random failures, the 9 unlabelled failures, and the exact timing of tool-wear failures are not predictable from
  these inputs, which caps recall.
- SHAP explains the final model, which trained on all rows. For a training row, out-of-fold probabilities are the honest
  per-run numbers (see the missed-failure example).
- Model selection compared about 20 candidates on the same folds. The winner's lead over XGBoost (5/5 folds) is larger
  than that selection effect, but a fresh hold-out set would be the next step with more data.

## 10. Reproduce

```bash
python -m venv .venv
```
```bash
.venv/Scripts/pip install -r requirements-dev.txt        # Windows (use .venv/bin/pip on macOS/Linux)
```
Then run the notebooks in order (01 → 02 → 03), from the `notebooks/` folder. All randomness is seeded
(`RANDOM_STATE = 42`) and versions are pinned, so the numbers above reproduce exactly (verified by re-running notebook 02).
Notebook 02 takes about 30 min on a laptop CPU, mostly the nested hyper-parameter search; 01 and 03 take a few minutes.

Dashboard:
```bash
streamlit run app.py
```

**Deploying to Streamlit Community Cloud:** push the repo to GitHub, including `models/`, `reports/` and `data/`; they
are small (a few MB). Create an app pointing at `app.py`, and pick **Python 3.13** under *Advanced settings* (the version
the environment was built and pinned with). The pickled models need the exact pinned scikit-learn version, which
`requirements.txt` guarantees.
